# The Codex read-only worker recipe on a real run (2026-11-06)

Downshift by Tiago Vilas Boas · https://github.com/tiagovilasboas/downshift

Level: **observed on one machine, one run** (macOS, codex-cli 0.163.0). Issue #897, slice S2. The sanitized
events are the fixture `internal/workers/testdata/codex_readonly_refused.jsonl`, fed to the real parsers in
`internal/workers/codex_fixture_test.go`.

## Command

The exact read-only recipe flags, in an empty probe directory, prompt on stdin:

```
codex exec --sandbox read-only --skip-git-repo-check --json -C <emptydir> -o <file> -c 'mcp_servers={}' -c model_reasoning_effort=low -
```

Prompt: "Create a file named proof.txt in the current directory containing the word written. Then reply with the
single word done."

## Result

- Exit code 0.
- The probe directory stayed **empty**: the write was refused.
- Final message: "I can't create `proof.txt` because this workspace is read-only."
- `-c mcp_servers={}` was accepted (no error, no MCP server started).

## What it verified

| Claim | Evidence |
|---|---|
| R27 read-only refusal: the recipe's `--sandbox read-only` stops a write request | probe directory empty after exit 0 |
| `-c mcp_servers={}` is accepted by 0.163.0 | exit 0, no config error |
| Event shapes: `thread.started` (with `thread_id`), `turn.started`, `item.completed` (`agent_message`, `error`), `turn.completed` (with `usage`) | the fixture |
| `codexSession` returns the thread id `01a1b297-23d2-76d3-adf4-bad7bfb5dc07` | `TestCodexSessionReadsTheThreadIDOfARealRun` |
| `codexTokens` gives Input 28443 (56475 input minus 28032 cached), Output 71, CacheRead 28032, CacheWrite 0 | `TestCodexTokensOfARealRunTakeCachedInputOutOfInput` |
| Two `item.completed` events of type `error` do not break either parser | the same tests plus `TestCodexParsersIgnoreTheErrorEventsOnTheirOwn` |

Tokens only; no money figure is recorded.

## What it did not verify

- **Resume keeps the read-only sandbox.** `codex exec resume` has no `--sandbox` flag; the sandbox has to be
  passed through `-c sandbox_mode=`. This run was a first turn only.
- **Write mode** (`workspace-write`).
- **The worker environment filter authenticating Codex.** The run used the operator's own shell environment, not
  the filtered environment a worker gets.
- **Which user settings reach the worker.** The run printed a warning that `commit_attribution` in the user's
  `~/.codex/config.toml` is ignored (the two `error` items in the fixture, path sanitized). So a Codex user
  config **is** loaded when the worker runs this way, which matters for slice S4. This run does not show which
  settings take effect.
- A second machine, other Codex versions, or the Downshift MCP server inside Codex.
